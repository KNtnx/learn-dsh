# 项目技术报告与复现方案工作流

当用户要求**分析、学习或调研某个项目**、或要求**写技术报告/复现方案**时，必须先加载本技能，并按下面的流程执行。

## 总则
- 信息收集用专用工具 collect_project_context，一次拿到结构化项目快照，比逐个 bash 探测更省 token。
- 补读源码用内置 read / grep，写作用内置 write；不要重复贴文件全文。
- 一切输出落在磁盘文件，不在对话里输出长篇正文。

## Phase 1 — 收集项目上下文（必做）
1. 调用 collect_project_context（无参数，默认抓取当前 cwd 的项目）。
2. 检查返回的 projectName、manifest、readme、agentsDoc、files、git 字段。
3. 若关键文件（入口文件、核心模块、测试）在 files 清单里但没有足够细节，用内置 read 补读其中少数几个关键文件（限制在 3-5 个，优先入口与核心逻辑）。

## Phase 2 — 创建输出目录
- 在工作区创建目录：learning-<projectName>（projectName 取 collect_project_context 返回的值）。
- 若目录已存在，直接使用，不覆盖已有文件；文件存在时追加或另命名。

## Phase 3 — 撰写技术报告（必做，写文件）
在 learning-<projectName>/ 下写 TECHNICAL_REPORT.md，固定结构，每节都要有实际内容（不要写"待补充"）：
# <项目名> 技术报告
## 1. 项目概述
<项目做什么、主要解决的问题、使用场景，基于 README 与实际代码>
## 2. 技术栈与依赖
<语言、框架、关键依赖及其作用；按 collect_project_context 的 manifest 归纳>
## 3. 目录结构
<基于 files 清单归纳主要模块与职责，给出树状或分组说明>
## 4. 核心代码分析
<入口、数据流、关键算法/模块；引用具体文件路径>
## 5. Git 状态
<当前分支、未提交改动摘要、最近提交动态（若存在）>
## 6. 构建与运行方式
<安装依赖、构建、运行的命令与前置条件>

## Phase 4 — 撰写复现方案（必做，写文件）
在 learning-<projectName>/ 下写 REPRODUCTION.md，固定结构：
# <项目名> 复现方案
## 1. 环境要求
<操作系统、语言版本、包管理器、网络要求，尽量具体>
## 2. 依赖安装
<逐条命令>
## 3. 复现步骤
<从克隆/进入目录到运行出结果的完整步骤，编号列表>
## 4. 预期结果
<运行后应看到什么输出/行为；可给出示例>
## 5. 验证清单
<如何确认复现成功：检查点列表>

## Phase 5 — 交付确认（必做）
1. 用内置 bash（ls）或 read 确认两个报告文件已存在。
2. 向用户简要汇报：报告所在目录路径、报告覆盖了哪些方面、复现方案要点（两三句即可，不要贴全文）。
